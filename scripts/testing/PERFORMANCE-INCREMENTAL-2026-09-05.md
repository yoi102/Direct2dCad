# 增量编辑与资源准备

日期：2026-09-05。承接同日的批量更新与并行缓存优化，保留工作区已有修改。

## 已实现

- 移动、旋转、缩放、镜像和复合路径几何命令只刷新受影响的块引用。命令独立执行时边界立即有效；变更结果标识已经包含依赖引用，Editor 不再重复解析。混合未解析变更的批次和结构变化仍走完整依赖检查。
- Handle 排序缓存使用独立的顺序版本。几何修改不重新排序；成员、图层、可见性、锁定、绘制顺序与实体替换会使缓存失效。
- 无单实体 grip 的大选择集支持局部边界更新。第一次局部修改建立边界树，之后每个修改项按 O(log N) 更新选择范围及集合移动点，包括范围缩回和排除锁定实体。大量实体同时变化时回退到线性重建，避免 O(N log N) 的树更新。
- 后台几何准备不再在 Schedule 中复制全图纸的点数组。所有者线程分批采集不可变快照，输入队列最多 64 项，已准备 geometry 队列最多 256 项。快照采集与资源挂接分别使用条数和时间预算；后台不访问可变实体。
- 有空间查询时，首次准备优先安排可见实体及其嵌套块定义。编辑使旧结果失效，取消及替换任务不阻塞等待工作线程。
- 用户 LOD、缩放预览设置、绘制顺序及打印路径均未改变。

## 边界

- 首次显示仍等待完整资源准备，避免逐步出现实体或漏绘。本次降低的是调用线程的长时间快照复制；尚未实现“可见区域就绪即首屏显示”。
- Schedule 仍一次采集实体 ID 数组及待处理 ID 集合；单个超大实体的点数组复制是不可抢占的，2 ms 为检查点预算，不是每次调用的硬上限。
- 局部选择更新仍会通知渲染器选择版本变化，不代表 GPU overlay 缓存可以全部复用。
- 没有缩小安全描边扩边，也没有改变 worker 的整画布纹理布局。这两项先用独立基准测量，避免以漏绘或合成顺序变化换性能。

## 编辑短基准

Release，BenchmarkDotNet Short，2 次预热、3 次测量；基准和测试套件顺序执行。

| 操作 | 原完整路径 Mean | 增量路径 Mean |
| --- | ---: | ---: |
| 20,000 个块引用，仅一个定义中的实体改变，影响 200 个引用 | 697.05 us | 9.45 us |
| 20,000 个选中实体，仅一个实体改变边界 | 2,434.22 us | 0.171 us |

块引用基准每次托管分配由约 1.32 MB 降为 33.9 KB。选择基准预热后已建立边界树；首次建树仍为 O(N)，不包括在这个稳定状态数字内。

这些是隔离操作，不包含命令历史、完整空间索引更新、属性面板刷新或 GPU 绘制，不能解释成帧率提升倍数。基线是保留的完整扫描/重建路径，并非切换 Git 版本进行整程序比较。

原始结果：`TestResults/incremental-optimization/editing-benchmarks/results/`。

```powershell
dotnet run -c Release --project Direct2dCad.Benchmarks -- --filter '*BlockDependencyUpdateBenchmarks*' '*SelectionGeometryUpdateBenchmarks*' --job Short --warmupCount 2 --iterationCount 3
```

## 渲染专项基准

- `StrokeQueryPaddingBenchmarks`：20,000 条线，另有一条视图外粗线，比较屏幕固定/空间线宽下的扩边、候选数量与空间查询耗时。控制台打印实际候选数。
- `ParallelSubmissionBenchmarks`：20,000 条线，1280/3840 宽度、10%/100% 的近似包围盒占屏面积，比较单线程、两个共享设备 context、两个独立设备。直接提交实体，不复用场景 tile/command list；如果并行路径失败则基准失败，不静默测量回退。
- 提交基准是 CPU 调用耗时，包含可能的驱动等待，但没有 GPU timestamp/fence 完成时间，不能单独用它归因显存带宽。占屏面积指实体整体包围盒，不是线条实际覆盖的像素比例。

```powershell
dotnet run -c Release --project Direct2dCad.Benchmarks -- --filter '*StrokeQueryPaddingBenchmarks*' '*ParallelSubmissionBenchmarks*' --job Short --warmupCount 2 --iterationCount 3
```

本机 Short 结果如下，原始报告位于 `TestResults/incremental-optimization/rendering-benchmarks/results/`。

| 线宽 | 显示方式 | 查询扩边 | 候选实体数 | 查询 Mean |
| --- | --- | ---: | ---: | ---: |
| 0.25 | 屏幕固定 | 16 | 100 | 0.420 us |
| 0.25 | 空间线宽 | 16 | 100 | 0.442 us |
| 20 | 屏幕固定 | 94.49 | 575 | 1.562 us |
| 20 | 空间线宽 | 100 | 648 | 1.699 us |

虽然候选量明显增加，但这个样本的绝对查询成本仍很小。这里没有据此修改空间索引或降低安全描边扩边；更密集的分布及候选后续处理仍需单独评估。

| 画布 | 近似占屏面积 | 单线程 | 两个独立设备 | 一个设备、两个 context |
| --- | ---: | ---: | ---: | ---: |
| 1280 x 720 | 10% | 15.50 ms | 8.30 ms | 16.82 ms |
| 1280 x 720 | 100% | 18.68 ms | 9.91 ms | 20.22 ms |
| 3840 x 2160 | 10% | 18.07 ms | 9.71 ms | 19.49 ms |

共享设备 context 没有在这个场景取得优势；不能把它当作默认升级方案。增大画布时三条路径都有开销增长，本轮未采用局部 worker 纹理或自适应切换。需要 GPU 时间与显存带宽采样，才能区分清屏合成、线条覆盖和驱动同步成本。已有完整场景缓存优先策略不变。
